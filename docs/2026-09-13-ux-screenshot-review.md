**LunchPick UX review — September 13, 2026**

The visual direction suits a small team lunch tool: restrained colors, readable body text, consistent controls, and a clear public voting journey. I would keep that direction. I would revise the GitHub button placement and the organizer pages' information hierarchy before considering the UX finished.

**Findings, in recommended implementation order**

1. **[P2] The new GitHub button overlaps page content.** On mobile Privacy, the floating circle covers the end of the retention paragraph. On the desktop closed-poll page, it overlaps a restaurant's metadata badge. This is a regression from the new placement, not a problem with the icon-only requirement. Keep the icon-only control and its accessible name, but give it a reserved position in the public header, organizer navigation, and standalone-page chrome. Avoid an overlay over the content area. The raised ballot bar prevents a direct collision with Save ballot, but does not solve the general overlap. Evidence: [mobile Privacy](/Users/jasonxu/Documents/personal/restaurant-voter/ux-review-screenshots-2026-09-13-feedback/04-privacy-mobile.png), [desktop organizer poll](/Users/jasonxu/Documents/personal/restaurant-voter/ux-review-screenshots-2026-09-13-feedback/15-admin-poll-closed-winner-desktop.png). Source: [root layout](/Users/jasonxu/Documents/personal/restaurant-voter/src/app/layout.tsx:62).

2. **[P2] A closed organizer poll does not prominently answer “Who won?”** The default view devotes its main panel to completed lifecycle steps, then presents a locked candidate roster without current results. The bright “Won” tag refers to a previous win, which can be mistaken for this poll's outcome. A poll closed without votes gets the same generic completion treatment. Replace the lifecycle panel with the actual winner and counts, or an explicit no-votes outcome. Distinguish historical wins from the current winner. Evidence: [closed winner](/Users/jasonxu/Documents/personal/restaurant-voter/ux-review-screenshots-2026-09-13-feedback/15-admin-poll-closed-winner-desktop.png), [closed without votes](/Users/jasonxu/Documents/personal/restaurant-voter/ux-review-screenshots-2026-09-13-feedback/17-admin-poll-closed-no-votes-mobile.png). Source: [default roster](/Users/jasonxu/Documents/personal/restaurant-voter/src/app/admin/polls/[id]/page.tsx:110).

3. **[P2] The tied organizer state gives contradictory instructions.** It says “Poll complete” and “the poll is now read-only,” then asks the organizer to choose a winner. On mobile, that required action is below the initial viewport. Lead with “Voting closed — choose a winner” and put the tied choices first. Move completed lifecycle history below the decision. Evidence: [mobile tied poll](/Users/jasonxu/Documents/personal/restaurant-voter/ux-review-screenshots-2026-09-13-feedback/16-admin-poll-closed-tie-mobile.png). Source: [completion copy and tie controls](/Users/jasonxu/Documents/personal/restaurant-voter/src/components/admin/phase-controls.tsx:113).

4. **[P2] Mobile layouts spend too much space before the task.** The dashboard repeats New poll, displays four large statistics, and adds filters before showing its first poll below the initial viewport. The ballot similarly spends its first screen on introductory content, large fallback media, and a disabled sticky save bar; the first selection control requires scrolling. Use a compact mobile summary, keep one prominent creation action, reduce empty-media height, and make the save bar less intrusive before a selection exists. Evidence: [dashboard](/Users/jasonxu/Documents/personal/restaurant-voter/ux-review-screenshots-2026-09-13-feedback/08-admin-dashboard-mobile.png), [ballot](/Users/jasonxu/Documents/personal/restaurant-voter/ux-review-screenshots-2026-09-13-feedback/22-public-voting-participant-mobile.png). Sources: [dashboard statistics](/Users/jasonxu/Documents/personal/restaurant-voter/src/components/admin/poll-dashboard.tsx:44), [sticky save bar](/Users/jasonxu/Documents/personal/restaurant-voter/src/app/globals.css:1335).

5. **[P2] Creating a lunch center requires technical knowledge.** The form requires latitude and longitude even though it also asks for an address. An organizer must obtain coordinates elsewhere and transcribe them, creating an avoidable setup hurdle and an opportunity for mistakes. Prefer address search or a map pin that fills the coordinates; retain manual coordinates as an advanced fallback. Evidence: [lunch centers](/Users/jasonxu/Documents/personal/restaurant-voter/ux-review-screenshots-2026-09-13-feedback/09-admin-lunch-centers-mobile.png). Source: [center form](/Users/jasonxu/Documents/personal/restaurant-voter/src/components/admin/center-form.tsx:19).

6. **[P2, fallback state] Google-data failure offers little recovery.** In this local run, nomination and history forms expose a missing API-key message, while restaurant cards repeat “Details unavailable” and consume substantial space with decorative placeholders. Voters cannot resolve a browser-key configuration problem. Use a short user-facing availability message, offer retry for transient failures, and preserve an external Maps link based on the stored Place ID. Compact missing-photo cards to help users compare names. Evidence: [nomination participant](/Users/jasonxu/Documents/personal/restaurant-voter/ux-review-screenshots-2026-09-13-feedback/20-public-nominations-participant-mobile.png). Sources: [configuration message](/Users/jasonxu/Documents/personal/restaurant-voter/src/lib/google/browser-loader.ts:23), [card fallback](/Users/jasonxu/Documents/personal/restaurant-voter/src/components/google/google-place-details-card.tsx:67). The missing key is a review-environment limitation; it is not evidence that production has this configuration problem.

**Limits of this assessment**

The screenshots cover the configured default states, not every interaction. They do not establish the usability of live Places search, photos, route estimates, map dialogs, selected/saved ballots, confirmation dialogs, validation errors, every organizer tab, keyboard navigation, or screen-reader announcements. The local Google Maps browser key was not configured, so live restaurant comparison still needs a separate review with working data. This is a visual and source-backed UX review, not an accessibility certification or a user study.

The UX findings above remain recommendations. Product changes during this task are the requested GitHub control and its ballot-bar clearance; the review additionally repaired the capture workflow.
